# 성능·메모리 점검 기록

점검일: 2026-08-11
대상: `release/web` 정적 빌드, Chrome headless, 1280×720

## 결론

- 예열 뒤 장면을 100회 전환해도 JS 힙, DOM 노드, 이벤트 리스너가 누적되지 않았다.
- 가장 큰 병목은 모든 고해상도 이미지와 이야기 음원을 시작할 때 한꺼번에 읽던 구조였다.
- 큰 시각 자산 8개를 같은 해상도의 WebP로 바꾸고 `title`, `story`, `home`, `pipes` 묶음으로 나눠 장면 첫 방문 때만 읽게 했다.
- 이야기 3편을 마치면 만화 텍스처와 디코딩된 음원 캐시를 해제한다. 집과 배관 자산은 재방문 시 끊김을 피하려고 유지한다.

## 자산 개선

| 항목 | 개선 전 | 개선 후 | 변화 |
|---|---:|---:|---:|
| 변환 대상 이미지 8개 | 10,614,894 B | 4,059,058 B | -61.8% |
| 전체 정적 자산 | 13,267,849 B | 6,712,013 B | -49.4% |
| 첫 화면 이미지 전송량 | 전체 이미지 일괄 로드 | 869,820 B | 시작 화면 2개만 로드 |
| 첫 화면 이미지 RGBA 추정치 | 66,258,000 B | 12,583,520 B | -81.0% |

배경 3개는 WebP 품질 88, 투명 스프라이트·집 부품 5개는 무손실 WebP를 사용했다. 모든 파일은 원본과 픽셀 크기가 같다. RGBA 추정치는 이미지가 브라우저에서 4 bytes/pixel로 완전히 펼쳐진 경우의 자산 텍스처 값이며, 브라우저·GPU의 실제 할당량과는 다를 수 있다.

## 브라우저 측정

### 시작과 캐시

- 새 저장 상태의 시작 화면 요청: `home-diorama.webp`, `quokka-poses.webp`만 요청했다. 이야기·집 세부 부품·배관 배경 요청은 없었다.
- 이야기에 들어갈 때 만화 3장과 OGG 3곡을 추가 요청했다.
- 이야기를 마친 뒤: 이야기 텍스처 0개, 이야기 오디오 캐시 0개, 활성 사운드 0개.
- 이야기에 다시 들어가면 자산을 다시 읽고, 정상 전환으로 집에 돌아오면 다시 모두 해제됐다.
- 로컬 시작 화면 표시: 470 ms. 시작 구간 최대 long task는 개선 전 288 ms에서 개선 후 140 ms로 줄었다.

### 장시간 전환

집·작업실·배관 지도·배관 내부·결과 화면을 먼저 한 번씩 예열한 뒤 100회 순환했다. 각 장면이 활성화된 뒤 100 ms를 두었으며 전후로 강제 GC를 두 번 실행했다.

| 지표 | 예열 직후 | 100회 후 | 변화 |
|---|---:|---:|---:|
| JS heap | 9,089,064 B | 9,054,956 B | -34,108 B |
| DOM nodes | 114 | 114 | 0 |
| JS event listeners | 97 | 97 | 0 |
| Documents | 1 | 1 | 0 |
| 활성 sounds | 0 | 0 | 0 |

콘솔 오류와 처리되지 않은 페이지 오류는 없었다. 이 결과에서는 지속적으로 증가하는 메모리 누수를 재현하지 못했다.

### 일반 모바일 조건 대리 측정

Chrome에서 4 Mbps 다운로드, 1 Mbps 업로드, 왕복 지연 100 ms, CPU 4배 감속, 915×412 가로 화면으로 캐시 없는 첫 접속을 측정했다. 이름 입력과 시작 화면이 조작 가능한 상태까지 6,389 ms였고 오류는 없었다.

이는 4 GB 실제 기기의 RAM·GPU 한도를 직접 제한한 측정이 아니라 네트워크와 CPU를 느리게 한 데스크톱 브라우저 대리 측정이다. 실제 저사양 Android 기기에서는 별도 확인이 필요하다.
